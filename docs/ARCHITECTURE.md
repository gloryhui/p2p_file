# 架构设计

> 状态：M0~M2 已实现并真机验证，M3（中继兜底）未开始。

## 1. 总体目标

两台设备跨公网直接传输文件。中心服务器只做**信令 / 发现**，数据尽量走 P2P 直连；
NAT 打洞失败时回退到中继（TURN / circuit relay），保证「能连上」优先于「一定直连」。

## 2. 分层结构

```
src/
  main.rs         CLI 入口，四个新命令（signal-server / serve / tunnel / push）的编排
  cli.rs          参数解析（clap）
  identity.rs     长期密钥对 → 节点 ID（ed25519）
  discovery/      节点发现
    mdns.rs         局域网组播发现
    signal.rs       信令服务器 + 客户端（公网交换候选地址与打洞令牌）
  nat/            NAT 穿透
    stun.rs         STUN Binding 请求，获取公网映射地址
    classify.rs     NAT 类型判定（EIM / 对称型）
    punch.rs       打洞状态机（同时开启 + 令牌鉴权）
    portmap.rs     UPnP IGD / NAT-PMP 主动端口映射（空壳）
  net/            把上面这些串起来：STUN → 候选收集 → 信令 → 打洞 → QUIC 端点
  tunnel/         通用 TCP 端口转发 + 文件直推 + 空闲重打洞
  transport/      数据通道（QUIC）
  protocol/       应用层协议：握手、文件清单、分片请求、控制消息
  transfer/       发送端 / 接收端、断点续传、进度
  crypto/         BLAKE3 分片校验、证书指纹校验
  storage/        临时文件与续传状态持久化
```

数据流：

```
   serve（家里那台）                  tunnel / push（外面那台）
        │                                    │
        └──── TCP 信令（只交换地址和令牌）────┘
                     │
              公网信令服务器（不碰业务数据）
                     │
        ┌────────────┴────────────┐
        │   UDP 同时打洞（同一 socket）
        └────────────┬────────────┘
                     │
          QUIC 直连（TLS 1.3 + 应用层双向认证）
                     │
        ┌────────────┴────────────┐
   文件流（Manifest）        隧道流（TunnelOpen → 转发到白名单目标）
```

## 3. 关键技术决策

| 关注点 | 选择 | 理由 |
| --- | --- | --- |
| 异步运行时 | `tokio` | 生态标准，QUIC / UDP 都基于它 |
| 数据通道 | `quinn` 0.11 | 多路复用流、天然流控、内建 TLS 加密；适合多分片并行传输 |
| TLS 后端 | `rustls` 0.23（经 `quinn::rustls` 复用） | 用 quinn 重新导出的版本，避免和 quinn 内部的 rustls 撞版本 |
| 自签证书 | `rcgen` 0.14 | 服务端每次启动生成一张，身份不靠它 |
| 加密 / 身份 | `ed25519-dalek` 3.0 | 公钥 → 节点 ID 自证，不需要 CA |
| 分片校验 | `blake3` | 快，支持增量 / 树形哈希，便于分片级校验 |
| 序列化 | `serde` + `postcard`（`alloc`） | 控制消息体积小、无 schema 依赖 |
| 局域网发现 | `mdns-sd` 0.21 | 自己搓 DNS 报文解析性价比太低，握手和 STUN 才是重点 |
| 网卡枚举 | `if-addrs` 0.15 | 取本机非环回地址，供 mDNS 公告与候选排序 |
| 命令行 | `clap` 4（derive） | 标准选择 |
| 日志 | `tracing` + `tracing-subscriber` | 结构化日志，`RUST_LOG` 可覆盖 |
| 端口映射 | `igd`（UPnP）、NAT-PMP | **尚未引入**，见 M3；先不占依赖 |

实际锁定的版本以 `Cargo.toml` 和 `Cargo.lock` 为准（`Cargo.lock` 应当提交，
因为这是二进制程序）。

### 备选路线

- **rust-libp2p**：`dcutr` 已经实现了打洞，配 `relay`（Circuit Relay v2）+ `kad` / `mdns`。
  开箱即用、久经验证，但抽象层厚，底层细节被藏起来，调试和定制成本高。
- **webrtc-rs / str0m**：ICE 负责打洞。若以后要和浏览器互通，选这条。
- **本方案（quinn + 自研打洞）**：既然是要「手搓」，走自研路线，能把 STUN、
  映射发现、同时开启的完整机制吃透。代价是代码量大、边界情况要自己踩。

## 4. 打洞流程（同时开启 Simultaneous Open）

```
   A               信令服务器               B
   │  注册/查询 ──────►│◄────── 注册/查询   │
   │◄── B 的公网端点 ──┤── A 的公网端点 ───►│
   │                   │                   │
   │  ① 双方各自向 STUN 服务器发 Binding 请求，得到自己的公网映射
   │  ② 双方几乎同时向对方的公网端点发 UDP 包
   │     └ NAT 因出站包建立映射，对方的入站包得以穿过 pinhole
   │  ③ QUIC 握手在打通的 UDP 四元组上完成
   │  ④ 定期 keepalive 保活映射（UDP 映射通常 30s ~ 120s 过期）
```

### 要点与坑

- **NAT 类型决定成败**：端点无关映射（EIM）+ 端点无关过滤（EIF）最容易成功；
  **对称型 NAT** 对每个目标分配不同端口，`①②` 拿到的映射不可复用，必须考虑
  端口预测（birthday paradox 式暴力探测）或直接走中继。
- **端口预测**：拿到多个 STUN 映射后可推测端口分配步长，双向扫一段端口区间提高命中率。
  这是很多成熟工具（如 WebRTC 的 ICE）内部在做的事，成本高但能救回一部分对称 NAT。
- **保活**：映射过期即连接静默中断，必须定时发包。
- **多网卡 / 多候选**：同时交换局域网地址、公网映射、IPv6 地址，全部并发尝试，谁通用谁。
- **双栈**：IPv6 通常没有 NAT，能直连就优先 IPv6，能省掉大半麻烦。
- **兜底必须做**：TURN / relay 回退不是可选项，否则在严格企业网里完全不可用。
- **安全**：打洞只解决连通性，不提供身份保证。必须靠密钥指纹 / 预共享码
  （类似短认证字符串 SAS）确认对面是不是目标节点，否则会把文件发给攻击者。

### 地址相关映射（ADM）：一个必须正面处理的坑

实测本机所在网络就是这种：向三个 STUN 服务器探测，拿到的公网 IP 相同但**端口不同**，
`classify` 判定为「地址相关（可以打洞）」。这意味着：

> STUN 探到的那个公网端口，**只对那台 STUN 服务器有效**。拿它去连对端，
> NAT 会另分配一个端口，对端看到的源地址和我们公布的对不上。

天真的实现（只在「源地址 == 候选地址」时才认下探测包）在这里必然失败，
而且失败得很隐蔽：日志显示打洞超时，看不出原因。

**解法：令牌鉴权 + 接受任意来源。**

1. 信令服务器为每一对节点生成一个 128 位随机令牌（`PunchToken`），随候选地址
   一起下发给双方，两边拿到的必须是同一个。
2. 探测包格式为 `PROBE_MAGIC || token || 16 字节随机填充`（填充每次不同，
   避免被中间设备按固定内容去重或缓存）。
3. 收到探测包时，**只要令牌对得上就认**，不管源地址在不在候选列表里；
   并把包里的**实际源地址**当作对端的真实地址记下来。

因为令牌是服务器发的、每次牵线都换新，所以「接受任意来源」不会变成
「接受任意人」——不知道令牌的扫描包一律丢弃。

令牌一致性由 `同一对节点拿到的令牌必须一致` 这条测试盯着：`try_pair` 必须
把**同一个**令牌发给两边，否则双方各认一个，谁也打不通谁。

### 空闲与重连：为什么 `serve` 要反复重新打洞

NAT 映射会在 30~120 秒没有流量后被回收。`serve` 要是在家里开一整天，
早上打的那次洞到晚上早就没了，对端再发包会被自家路由器直接丢掉。

所以 `serve` 是一个循环：**等对端 → 打洞 → 服务 → 空闲超时 → 回到等对端**。

- 每一轮都必须拿一个**干净的 socket**：打洞和 QUIC 必须复用同一个本地端口，
  而上一轮的 socket 已经交给 QUIC 了，收不回来。
- 空闲判定要小心 `tokio::select!` 的守卫：`if active == 0` 这种写法只在进入
  select 的那一刻求值一次，之后不会重算。结果就是——进入时已有连接 → 计时
  分支被永久禁用 → 再也不会重新打洞；进入时还没有连接 → 计时到点又会不看
  当前状态直接拆掉活跃会话。守卫必须写在分支体里，等计时真到点了再判断。

### 打洞失败 ≠ 连不上

打洞的唯一目的是**在 NAT 上开映射**。只要我们的探测包发出去了，本机这半边
映射就建立了；对端可能已经收到，只是它的回应还没回来。所以打洞没收到回应时
不能直接放弃，而应该**按候选顺序逐个尝试连接**，让 QUIC 自己的重传去撞门。

这一点在实测里很关键：`serve` 正在服务一条隧道时不会去打洞，此时对端只能靠
这条兜底连上（日志里能看到「打洞未确认 → 换用了后面的候选地址」）。

### 信令服务器的一个坑：读取出错也必须清场

节点下线时要从在线表里摘掉。容易写错的地方是：读循环里用 `?` 直接返回，
于是**只有**干净关闭（`Ok(None)`）才走到清理代码，而对端被 `kill -9` 时读到的是
RST（`Err`），提前返回，节点就永远留在「在线」表里——服务器随后会把**过期的
候选地址**发给别人，对端照着打洞只能打到空气上。

正确做法是两条路都走清理。这条有专门的回归测试（用裸 `TcpStream` 配
`SO_LINGER=0` 确定性制造 RST；注意 `into_split` 出来的两个半边共享同一个 fd，
只 drop 一半并不会真正关闭连接）。

## 4.5 信令协议

极简的 TCP + 长度前缀 postcard，**只牵线，不碰业务数据**：

```
[u32 小端长度][postcard 负载]
```

| 消息 | 方向 | 用途 |
| --- | --- | --- |
| `Register { node_id, public_key, candidates }` | C→S | 登记自己 + 公布候选地址 |
| `Registered` | S→C | 登记完成 |
| `Lookup { node_id }` | C→S | 查对端 |
| `PeerCandidates { node_id, candidates, token }` | S→C | 对端已就位，附上打洞令牌 |
| `PeerPending { node_id }` | S→C | 对端还没上线 |
| `Ping` / `Pong` | 双向 | 保活 |
| `Error { reason }` | S→C | 出错 |

服务器内存里维护 `peers`（在线节点 → 候选地址 + 发送队列）和 `waiters`
（谁在等谁上线）。牵线时机有两个：对方登记时唤醒等待者、以及自己主动查询时。
两处都可能触发，所以同一对节点可能被牵线两次——这也是令牌一致性测试存在的原因。

客户端**必须一直持有**这条连接：一旦 drop，服务器就认为本节点下线，
对端之后再也查不到我们。`DirectLink` 持有 `SignalingClient` 就是为了这个。

## 4.6 通用 TCP 隧道

一条 QUIC 连接上，每条被转发的 TCP 连接开一条独立的双向流（避免队头阻塞）。
流的第一个帧决定这条流干什么：

| 首帧 | 后续 |
| --- | --- |
| `Manifest` | 走文件接收流程 |
| `TunnelOpen { target }` | 连到 `target` 并把字节双向搬运 |

`target` 必须在 `--forward` 白名单里，且只接受 `IP:port`（不接受域名，
免得用 DNS 绕过白名单）。

搬运用 `tokio::io::copy_bidirectional` 的等价手写实现（`splice`），
两个方向各自独立，任一方向结束就关掉这条流。

## 5. 文件传输协议要点

- **分片**：固定大小分片（建议 256KB ~ 1MB）；每片单独校验、单独重传。
- **清单（manifest）**：文件名、大小、分片大小、每片 BLAKE3、整文件根哈希。
  接收端拿到根哈希后先确认，再开始收数据。
- **断点续传**：接收端持久化「已校验分片位图」，中断后只补缺失分片。
- **并行度**：QUIC 多流并行拉取分片，配合流控避免打爆对端。
- **落盘**：先写临时文件 + 位图，全部校验通过后再改名为目标文件，避免半成品被误用。

真实验证过的行为（不只是单测）：

- 两个真实进程之间传输 3.8 MB 文件，15 个分片，sha256 一致，无 `.part`/`.bitmap` 残留，Ctrl-C 正常退出。
- 手写 STUN 对 `stun.l.google.com`、`stun.miwifi.com`、`stun.fitauto.ru`、`stun.cloudflare.com` 均成功取回公网映射。其中 Cloudflare **必须带 FINGERPRINT** 才应答，这也是补上指纹校验的原因。
- 密钥文件权限确认为 `0600`。
- `scripts/e2e.sh` 起三个真实进程（信令服务器 / serve / tunnel）跑完整链路：
  打洞成功 → 隧道转发 1MB 随机数据无损 → 直推 2MB 文件 sha256 一致 →
  断开后 serve 重新打洞 → 再连一次仍然成功。全部通过。
- 实测本机 NAT 为「地址相关（可以打洞）」，正是需要令牌鉴权才能打通的类型。
- 实测 `serve` 正在服务隧道时不再打洞，对端靠「候选顺序重试」兜底连上
  （日志确认走到了这条路径）。

### STUN 实现说明

- 只实现 Binding 请求/响应，不做认证（用不着：认证在应用层握手）。
- **总是**附带 FINGERPRINT（`0x8028`），CRC-32/ISO-HDLC 后与 `0x5354554E` 异或，必须是最后一个属性。
- 收到带 FINGERPRINT 的报文会强制校验；不带指纹的报文仍然接受（兼容老服务器）。
- 地址属性同时支持 IPv4 与 IPv6 的 XOR 编码。
- 校验时按事务 ID 过滤，避免把别的报文（比如打洞探测包）当成 STUN 响应。

### 已知问题 / 下一步

1. **对称型 NAT 无解**，必须做中继（M3）。目前只能靠路由器手工端口映射 +
   `--advertise` 绕过。
2. `classify` 只判映射行为，没判过滤行为（需要 `CHANGE-REQUEST` 支持）。
3. 只绑 IPv4。候选地址里的 IPv6 链路本地地址已被过滤掉（出了路由器没用），
   全局 IPv6 要等双栈监听做完才能真正用上——而 IPv6 通常没有 NAT，
   能直连就省掉大半麻烦，值得优先做。
4. 打洞没有端口预测（birthday paradox 式扫描），对称 NAT 下救不回来。
5. 文件读写用的是同步 IO，跑在大文件时会阻塞异步执行器，应挪进 `spawn_blocking`。
6. 分片数据和控制消息共用一条流，应拆成独立单向流。
7. `serve` 空闲后会回到「等对端」状态，此时它在自家 NAT 上没有映射。
   这没问题（重新打洞时映射会重建），但意味着对端必须能通过信令唤醒它——
   如果信令服务器挂了，已经建立的隧道会继续工作，但断线后无法重连。
8. `transport::quic` 跳过证书校验是**有意**的，前提是每次连接都必须跑完应用层握手；
   这个约束不能破坏。
9. 信令服务器是单点，且重启后在线表清空（客户端会重新登记，但需要一次重试）。
   另外它对客户端没有鉴权——任何人都能登记节点 ID。这不影响数据安全
   （数据不经过它，且应用层有双向认证），但可以被用来骚扰牵线。
