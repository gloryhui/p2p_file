# ADR-005：单文件执行、双端暂停与持久完成回执

状态：T006 实施决策。目录展开、重名备份事务、全局调度和完整任务 UI 分别由 T007–T010 接入。

## 所有权与后台边界

`TransferService` 持有 T003 TaskStore 的唯一写入所有权，UI 不再保留第二个可变任务库。文件扫描、源身份重验、chunk 读写、checkpoint、发布和任务快照提交都通过 `spawn_blocking` 执行；Tokio 网络线程只编排有界消息和状态。读取快照不发送变更通知，避免 UI 订阅产生反馈循环。任务状态与每 250 ms 合并的进度通过 watch 通知可供后续任务列表读取；进度提示不作为续传依据。

已认证并完成 T005 能力协商的 session 为每个 peer 启动一个 `accept_bi` 分发器；业务模块没有新的 UDP reader、身份握手、信令连接或 tunnel。入站每 peer 最多 8 条待处理流；当前最多 3 个活动文件任务且每 peer 一个，超限返回可重试 Busy/诊断，不构建 T008 队列。session 的有界命令入口提供 SendFile、PauseTask、ResumeTask；完整按钮和任务列表仍由 T010 接线。配置接收目录仅影响新任务，恢复始终采用记录里的根目录。

显式重配置和 session 退出先取消异步任务，再递增业务 epoch 并将非终态活动记录持久标记 Interrupted。已经排队、尚未取得任务库锁的旧 epoch 写入不得再提交；已在锁内完成的持久回执优先保留。阻塞 chunk 写入即使在取消后完成，也只是对应 `.part` 的已验证数据，重开仍按 bitmap/哈希重验。网络断开会排空子任务的错误清理路径；不依赖 Drop 删除或提交接收数据。

## 本地记录与文件流

TaskRecord 增加向后兼容的可选 `file_details`，包含相对名称、完整清单、publish_prepared 和 receipt_committed。TaskId、peer、方向、本地路径、清单与相对名称一旦创建不可变。新增字段不改变旧记录；旧版本遇未知字段会保留并拒绝快照，而不是静默降级。任务快照仍有 16 MiB 上限，写入端也在替换前检查，不能生成下次无法读取的超限文件。

本阶段仅接受一个合法 UTF-8 basename；不接受目录条目、路径分隔符或 group。源文件必须是用户明确选定的普通文件，拒绝 symlink/reparse point 和非 UTF-8 本地路径。入队前生成清单，继续前完整重算；每片还核对打开文件与当前源路径的 inode/file ID、长度和 chunk 哈希，因此删除、替换和内容变化不会沿用旧内容位图。源路径只在本机记录和文件句柄中存在。

每条双向文件流只绑定一个任务。首帧为 Offer，已有任务需要匹配原 peer、方向、相对名称和整个清单；未知任务先持久创建并排入 Queued，再转入 Connecting/Negotiating/Transferring。每次独立流尝试重置双方序号，不能在同一流内重复 Offer。T005 Message 追加 RequestChunk(10)、Chunk(11)、ChunkAck(12)，没有改变旧桌面或 CLI discriminant。

接收端返回重验得到的 Resume bitmap，以 4 个请求窗口拉取。单 chunk 最大 1 MiB，默认 256 KiB，整帧仍为 4 MiB 上限。控制/数据共用该任务有序双向流，独立 reader 将完整帧放进容量 8 的 channel；选择暂停不会取消半个 frame read。双方检查序号、任务、方向和索引，执行器另检查请求/确认集合，拒绝重复或未请求数据。正常空文件也经过持久发布和回执。

远端 Continue 使用一条新的控制流，只有 TaskId。发送方从该认证 peer 的已保存 Paused/Interrupted 或可重试 Failed 发送任务找源文件，验证后确认，再建立新的 Offer 文件流。接收方不能指定或改写发送端路径。清理旧尝试期间的新继续有五秒等待上限，活动任务不能被重复请求接管。

## 暂停与竞态

本地暂停先进入 Pausing，停止补充请求。已有请求继续有界处理；receiver 在所有在途 chunk 处理完后强制 checkpoint，再发送绑定 pause_request_id 的 Paused。sender 发起暂停时等待此确认；receiver 发起暂停时，sender 同时发出自身 Pause 请求，确保自身也等待 receiver 的 checkpoint 确认，不能在回一个 Paused 后就过早关闭流。双方同时暂停合并到同一状态，重复本机点击不重复发帧。

等待暂停确认的阶段有五秒 deadline；单次网络读写也有独立有界超时。超时或断流转 Interrupted，receiver 尽力 checkpoint 并保留 `.part/.bitmap`，没有任何暂停、退出或错误路径调用 discard。协商阶段收到暂停先记录 Pausing，Resume 到达后发出 Pause；若未能协商则按 deadline 中断。

最后一片与暂停相遇时，receiver 若完成全部校验则执行 Finalizing；持久回执提交后保持 Completed，迟到错误不会回退完成状态。sender 只有收到匹配 root 的 Completed 才提交自身回执；连接在确认前消失时保守记录 Interrupted，手动继续后向 receiver 取回已持久回执。

## checkpoint 与发布前后窗口

每个接收任务在已保存根目录下使用 `.p2p-desktop/<peer-id>/<task-id>/` 隔离状态文件，不能拿网络路径作为 `.part/.bitmap` 文件名目录。复用已有 PartialDownload 写片和恢复校验；默认 64 MiB 或 1 秒触发 checkpoint，暂停与发布前强制执行 `sync_data → bitmap snapshot/persist → durable bitmap`。未 checkpoint 片可以重传，损坏片在恢复时清位。

storage 仅增加 `prepare_desktop_publication`：完整性检查、强制 checkpoint、sync_all、关闭句柄，保留 staging inode 和 bitmap。原 CLI finalize/no-overwrite 编号语义不变。

T006 对空目标采用最小发布事务：

1. 数据完整并同步，任务库持久记录 Finalizing/publish_prepared。
2. hard_link 原子 no-replace 发布目标；已存在时仅当目标和 staging 是同一个 inode/file ID 才认定为本任务上次发布。
3. 同步文件与 Unix 父目录，复核目标清单。
4. 在同一个原子任务快照中提交 receipt_committed 和 Completed。
5. 清理 staging 的可清理文件，再发送 Completed；清理失败不会撤销已经持久的回执。

目标同名且内容相同也不能冒认完成，必须证明文件身份属于该 staging。发布成功但回执未提交时，重开由保留的 staging inode、目标文件 ID 和内容校验补提交回执；已有回执则直接重发 Completed，不重复发布。sender 未确认的任务可以幂等重试。

已有不同 inode 的目标暂时明确失败并保留 `.part`，不覆盖、不自动编号。T007 将以此边界扩展备份旧文件、目录结构和完整可恢复 journal。Windows 使用 GetFileInformationByHandle 取 volume/file index；Unix 使用 dev/ino。Windows 发布文件以读写句柄 FlushFileBuffers；std 没有可移植的 Windows 目录 fsync，不能宣称硬件掉电绝对一致。

## 可验证证据与边界

测试包括真实 loopback QUIC 双端互传、空文件、三种暂停发起方式、最后一片竞态、暂停超时、完成帧被切断后的回执重放、源变更/替换/消失、错误 peer、同内容目标冲突、发布后回执前恢复、位图篡改重验、session 命令到被动 peer 的接线。

进程测试通过当前 test executable 的专用子进程入口运行真实双方、持久身份与任务库。自然 checkpoint 后分别对 sender/receiver 调用操作系统 hard kill，存活端正常退出，重新启动双方并显式继续 70 MiB 文件，验证已重验的 durable 分片、完整清单和双方回执。同步门仅在 `cfg(test)` 下存在，没有生产环境变量或故障开关。这个测试不是 Drop 模拟，也不是两地 NAT 证明。

原生 Windows 10/11、Apple Silicon 人工交互、真实双 NAT 和目录重名故障矩阵仍待后续指定任务。T006 完成不等于完整桌面 MVP 发布验收。
