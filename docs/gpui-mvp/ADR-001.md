# ADR-001：T001 的 GPUI 版本、平台边界与桌面壳

状态：T001 实施决策，待控制层复核

## 决策

本仓库的桌面入口使用 gpui = "=0.2.2"，通过可选 gui feature 暴露
p2p-desktop 二进制。默认 p2p_file CLI 不引入或初始化桌面运行时。桌面代码位于
src/desktop/，入口位于 src/bin/p2p-desktop.rs。

T001 只验证原生桌面窗口、文本输入、系统剪贴板和原生路径选择器。它不生成身份、
不建立连接、不发送或接收文件，也不把按钮点击显示成网络成功。真实身份和传输由
后续任务接入。

## 版本证据与不混用 API

- crates.io 当前可直接解析的官方 gpui 包为 0.2.2；本工作树通过
  cargo info gpui --verbose 和下载的源码核对了 Application、WindowOptions、
  EntityInputHandler、prompt_for_paths、剪贴板及各平台模块。
- Zed 当前主线 README 已展示更新后的 gpui/gpui_platform 分拆调用方式。这是
  当前主线参考，不是本 ADR 的依赖 API；T001 不把 gpui_platform::application()
  或主线示例混入 0.2.2。
- gpui-kit 0.6.6 的发布说明明确其 gpui-pre 是 exact snapshot pin；本地
  cargo info gpui-component --verbose 显示 0.6.6 依赖 gpui-base=0.6.6 和
  gpui-pre = =0.3.6。因此 T001 不添加 gpui-kit/component，避免两个不兼容的
  GPUI 版本族。

参考：

- https://github.com/zed-industries/zed/blob/main/crates/gpui/README.md
- https://github.com/longbridge/gpui-kit/releases/tag/v0.6.6
- https://crates.io/crates/gpui/0.2.2

## 壳层实现与输入正确性

TextField/TextFieldElement 以 gpui 0.2.2 的 examples/input.rs 为适配基础，保留其
EntityInputHandler、IME marked range、UTF-16 选择、系统剪贴板和鼠标选择的工作
方式；本仓库的改动、产品状态和许可归属记录在 THIRD_PARTY_NOTICES.md。

T001 特别覆盖：

- UTF-16 与 UTF-8 的双向换算，含中文和 surrogate-pair emoji；
- IME 新选区以新文本为坐标系，再加插入点，避免多字节前缀造成非法边界；
- GPUI 的 secondary-* 键绑定，使 macOS Command 与 Linux/Windows Ctrl 都能
  使用复制、粘贴、全选和剪切；
- 绘制布局陈旧时，鼠标索引安全返回，不对 placeholder 或尚未重绘的内容作断言；
- 本机 Node ID 为只读的 T002 占位，复制按钮只报告“尚未接入”，不会写入伪 ID；
- 多文件列表固定高度、Y 轴滚动，单行路径使用 GPUI truncate，适配最小窗口和长路径。
- 根容器使用 GPUI 0.2.2 的 `id("desktop-shell").overflow_y_scroll()`，因此
  760×560 最小窗口可以滚到连接/选择器取消状态，而不是把状态栏裁掉。

## Linux

CI 的 Ubuntu job 在 `.github/workflows/gpui.yml` 中安装 GPUI 默认 Linux 后端需要的
fontconfig、freetype、Wayland、X11/XCB 和 xkbcommon 开发包，并执行 locked
check/build、显式 GUI 测试和 GUI Clippy。本地还用命令级安装补齐了 XCB/xkbcommon
链接包、Mesa Vulkan 驱动、`xdotool`、`xclip`、ImageMagick，以及原生路径选择器
所需的 `xdg-desktop-portal`/GTK 后端、D-Bus 和 Openbox；没有修改全局 Cargo 配置。

软件显示验证使用 `Xvfb` + Mesa `llvmpipe`；它证明窗口、渲染和输入路径，不能
替代真实 GPU 或真实桌面会话。无窗口管理器时，首个 Xvfb capture 在等待三秒后
仍为 217-byte 黑帧，resize 才触发 expose；这被记录为测试环境差异，未向生产 UI
加入轮询重绘 hack。用同一 Xvfb 加 Openbox、D-Bus 和明确 `windowfocus` 后，未经
resize 等待 expose 的首帧稳定渲染并已视觉复核；随后在新 display 先等待
`_NET_SUPPORTING_WM_CHECK` 再启动 GUI，无 resize/focus 也得到稳定首帧。完整命令、
窗口 ID、截图和取消状态见 [T001 Linux evidence](evidence/README.md)。

GPUI 0.2.2 的 Linux 平台通过 `ashpd` 调用
`org.freedesktop.portal.FileChooser`，没有 zenity fallback；T001 在 GTK portal
启动后实际打开 `Open File`/`Open Folder` 并用 Escape 验证文件、发送目录和接收
目录三条取消路径。

## Windows 10/11

GPUI 0.2.2 自带 Windows 平台源码的证据如下，不能只用 Zed 网站推断：

1. src/platform/windows/direct_write.rs 的 DirectWriteComponent::new 注释说明
   IDWriteInMemoryFontFileLoader 从 Windows 10 Creators Update 开始支持，因此
   DirectWrite 文本系统的最低相关边界是 Windows 10 1703（Creators Update）或更高。
   创建工厂、内存字体 loader 和 GPU state 都返回 Result，失败沿初始化错误路径
   传播。
2. src/platform/windows/events.rs 的 get_client_area_insets 对
   WindowsVersion::Win10 和 WindowsVersion::Win11 分支分别计算非最大化窗口顶部
   inset，不能把两者的原生标题栏几何混为一谈。
3. src/platform/windows/util.rs 的 configure_dwm_dark_mode 调用
   DwmSetWindowAttribute(...).log_err()；DWM 属性失败会记录错误，不应被壳层当作
   身份/传输成功或未处理 panic。

Zed Windows 开发文档要求 Visual Studio/MSVC C++ 工具、C++ Spectre 库、Windows
10/11 SDK（文档列出的最低 SDK 为 10.0.20348.0）和 CMake。这是构建 Zed 的环境
说明，不是把 SDK 版本误报为 GPUI 的最低运行系统。T001 的 Windows CI 使用
windows-2022 进行真实交叉目标编译；它不能代替 T012 在 Windows 10 22H2 上的
原生窗口/输入/剪贴板 smoke test。T012 必须记录 Windows SDK、MSVC、实际 OS 版本、
窗口创建、Ctrl/Command 等价快捷键、DWM 错误处理和最小窗口行为。

参考：

- https://zed.dev/docs/development/windows
- gpui 0.2.2 源码：src/platform/windows/direct_write.rs、
  src/platform/windows/events.rs、src/platform/windows/util.rs

## macOS

T001 的 macOS CI 目标为 `aarch64-apple-darwin`，只做 macOS-14 runner 的真实编译
检查。GPUI 0.2.2 默认 macOS 路径使用原生平台模块/Metal；其固定源码
`build.rs::compile_metal_shaders` 明确向 `xcrun metal` 传递
`-mmacosx-version-min=10.15.7`。这是 GPUI 0.2.2 的 shader 编译下界证据，不是
本项目已经在 macOS 10.15 或 13 上运行通过的声明。

产品文档的 Apple Silicon 目标仍为 macOS 13+；T001 没有把 CI runner 或源码编译
下界误报为产品兼容性。T012 必须提供 macOS 13+ Apple Silicon 真机/可复现 VM，
记录 `sw_vers`、`xcodebuild -version`、`rustc -Vv`、实际 deployment target，
并执行原生窗口首帧、760×560 最小尺寸、Command-A/C/V、中文/emoji/IME、原生
文件/目录面板取消和高 DPI 截图。该 smoke test 在本 worker 未执行。

## 可复现命令与证据边界

本轮 Linux worker 的实际工具链为 `rustc 1.98.1 (48a229cea 2026-09-01)`、
`cargo 1.98.1 (797e8a9bc 2026-08-05)`，主机为 Ubuntu 24.04 x86_64。最终 head
使用以下命令复核：

```sh
cargo fmt --all -- --check
cargo check --locked --offline --features gui --bin p2p-desktop
cargo test --locked --offline --features gui --lib desktop::tests
cargo clippy --locked --offline --features gui --all-targets -- -D warnings
cargo build --locked --offline --features gui --bin p2p-desktop
```

Ubuntu CI 的依赖安装命令与三目标矩阵固定在 `.github/workflows/gpui.yml`；本地
运行时命令、portal 启动方式、首帧差异、DPI `GPUI_X11_SCALE_FACTOR=1.5` 实测
（窗口从 960×680 logical 变为 1440×1020 physical）和每张可访问 PNG 均索引于
[evidence/README.md](evidence/README.md)。Windows 10 和 macOS 原生 smoke 需要
T012 提供设备后执行，当前明确为未执行，而不是“编译即通过”。

## 验收与可恢复性

cargo fmt --check、核心 Rust 测试、Clippy、GUI 编译矩阵和 Linux 窗口/交互证据
必须有独立证据。PR 只引用总控 Issue，不关闭总控 Issue。Windows 10 和 macOS
原生 smoke 未由 T001 执行，必须由 T012 提供设备并复核；这项边界不能被软件显示
或 runner 编译替代。
