# ADR-006：目录条目、能力路径与可恢复重名发布

状态：T007 实施决策。固定验收文档 ref 为 `2041a38756b87ba7856dcd343624d98df2283c5a`；本 ADR 不改写验收标准。T008 负责全局队列、公平和目录聚合 UI 状态，T010 负责完整选择器和按钮。

## 目录选择与持久绑定

目录扫描在 blocking worker 上执行，保留用户所选顶层目录、所有子目录和空目录。目录使用真实 `Entry::Directory` 与 `DirectoryTaskDetails`，没有伪造零字节文件清单。子文件保留完整相对路径、清单、同一随机 group_id 以及仅本地保存的 source_root。发送路径和接收根不出现在协议中；Continue 仍只含已授权 TaskId。

扫描上限为 4096 条目、64 层相对路径、131072 个总 chunk；单文件继续遵守 65536 chunk、1 MiB 最大 chunk 和任务快照 16 MiB 上限。遍历、每次文件读取和最终提交前检查取消标志。取消读取返回不可自动重试的 I/O 错误，避免 Read 的 Interrupted 自动重试形成循环。取消或扫描失败不会创建部分任务组；完整扫描后一次快照提交全部稳定任务 ID，再持久入队。启动中断恢复沿用已有 ID，不自动重扫或重传。

当前目录选择按确定性遍历顺序逐条执行，文件仍使用 T006 暂停与 checkpoint；T008 将接入真正的 FIFO/1—3 并发与公平调度，不能将本阶段称为已具备公平队列。每条目录控制流和文件流复用已认证连接，接收端完成目录创建/同步与持久回执后才回 Completed。文件/目录类型冲突保留旧内容并明确失败。

同一目录组首条接收记录固定接收根。之后的新子条目采用该认证 peer/group 的根，设置变更不会把一个已开始的目录组拆到两个接收目录。任务 group、相对路径、目录类型和源绑定均不可改变。

T007 追加必需能力位 `CAP_DIRECTORY_TRANSFER = 32`，当前 Hello 为 63。T006 仅文件执行的 Hello(31) 和更早 schema-only 桌面构建均明确拒绝。旧 CLI ControlMessage 和桌面既有 discriminant 不变。

## 路径与文件系统边界

继续使用 '/' 分隔的 UTF-8 相对路径，拒绝穿越、绝对路径、盘符/UNC、反斜杠、ADS、设备名、控制字符、尾随点/空格、超限组件和深度。`.p2p-desktop` 在任何组件中均为保留内部命名空间，大小写变体也拒绝。扫描拒绝所有 symlink、junction/reparse point 与非普通文件，不静默跳过。

GUI 引入可选、锁定版本的 cap-std/cap-fs-ext，目录操作相对已打开句柄执行。[Dir API](https://docs.rs/cap-std/3.4.6/cap_std/fs/struct.Dir.html) 与 [open_dir_nofollow](https://docs.rs/cap-fs-ext/3.4.6/cap_fs_ext/trait.DirExt.html) 是此实现的基础。显式选择/配置的根是 ambient authority 边界；根以下逐组件打开 no-follow 目录，文件最后组件也使用 no-follow。接收文件创建、恢复 bitmap、journal、硬链接发布与清理均使用相同目录能力，不把检查后的 ambient 路径重新交给 std::fs 写入。

句柄固定的是已授权目录对象。外部进程把一个已打开目录改名后，操作仍绑定该对象，不跟随原名称处新建的链接；恢复时 journal 的父目录 ID 必须匹配，不能把旧 journal 用到替换目录。模型不承诺抵御同一 OS 用户直接删除/修改自己的私有 staging 或修改已完成文件；这种修改可使恢复失败，但不能成为向任意新路径写入的协议能力。私有 staging 的普通文件与 bitmap 链接被明确拒绝。Unix 文件打开使用 O_NONBLOCK，在检查普通文件类型前不会等待 FIFO 对端；正常磁盘文件行为不变。

NFC 规范化与 Unicode 先转大写再转小写并再次 NFC 的保守 key 检查扫描中同级碰撞和已有目标别名；发现不支持的编码或碰撞明确报错。该保守策略覆盖 final sigma、dotless i 和展开的大写别名，宁可明确拒绝额外别名，也不静默替换或合并名称。平台本身不能同时表示的源名不是两个独立目录条目；Linux 在可表示两个名字的文件系统上验证实际扫描碰撞，所有平台验证 key 与已有别名拒绝。

新 GUI staging 使用固定 `data.part`/`data.bitmap` 内部名，支持 255 字节合法 basename，不因附加 hash 后缀超过文件系统限制。T006 已存在的旧 staging 文件名仍可恢复。清理跳过从未创建的超长旧格式名称，且持久回执重发时重试暂存清理；最长 basename 回归断言发布后 data.part 已移除。CLI staging 和发布规则保持原状。

## 发布 journal 与外部竞争

文件完整且强制 checkpoint/sync_all 后，关闭数据写句柄，记录 peer/TaskId/相对目标/清单 hash/staging 文件 ID/父目录 ID/旧文件 ID/固定 UTC 毫秒备份名。journal 存于该任务私有 staging，通过同步临时文件与原子替换持久化，读取有 64 KiB 上限且校验所有绑定。损坏记录明确失败，不能 panic 或猜测完成。

发布由唯一 TaskStore writer 的 mutex 串行执行；当前是比逐目标锁更强的全局发布序列，锁内没有网络 await，所有磁盘工作在 blocking worker。流程为：

1. PREPARED journal 与 TaskStore publish_prepared 持久化。
2. 若原目标是普通文件，原子 no-replace 移到固定时间戳备份；同步目标父目录，再写 OLD_BACKED_UP。
3. 新 staging 原子 hard-link/no-replace 到原名；同步目录，写 NEW_PUBLISHED。
4. 复核正式文件身份、长度与全部清单；在同一任务快照提交 receipt_committed + Completed。
5. 写 RECEIPT_COMMITTED，清理可清理暂存，再发送 Completed。回执后清理失败不撤销成功。

Linux 使用 renameat2(NOREPLACE)，macOS 使用 renameatx_np(RENAME_EXCL)，均由 rustix 提供；Windows 使用源文件句柄的 NtSetInformationFile(FileRenameInformation)，ReplaceIfExists=false，并以固定目标目录句柄解析相对名。[Windows NtSetInformationFile](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntsetinformationfile) 定义该操作与 DELETE 权限。cap-std 的 Windows 目录句柄不共享删除，目录使用期间不可被改名/删除；测试必须先释放能力句柄再清理 fixture。没有 exists()+普通 rename 的覆盖窗口，也没有失败后回退覆盖。

备份名示例 `report+20260926T043012123Z.txt`。同时间戳被占用时增加 `-1/-2`；每个候选在尝试移动前写入 journal。备份不能覆盖已有文件。若添加时间戳后组件超限，明确失败并保留原文件和新数据。

恢复根据实际文件 ID 和 journal 阶段核对：备份移动已完成但 journal 未推进时复用指定备份；新目标已发布但回执未提交时必须与 staging 同一文件且全清单匹配；已有回执直接重发 Completed。只凭“内容相同”不能认定已发布。外部进程抢占原名不被覆盖，保留旧备份和 staging 等待处理；外部替换正式文件会阻止未提交回执。CLI 的原 no-overwrite 编号策略完全保留。

Unix 目录句柄可能是仅定位的 O_PATH，fsync 通过能力句柄重新打开 '.' 的读目录执行。Windows std 没有可移植目录 fsync；文件 FlushFileBuffers、journal/快照原子更新与保守重验仍有效，但不承诺硬件掉电绝对一致。

## 验证和范围

本地测试覆盖实际认证 QUIC 目录结构/中文/空条目/重名，取消/扫描上限，非法 portable 名称、源链接、staging 链接、目标链接与目录句柄替换，实际两线程同目标发布，时间戳撞名，外部抢占/回执前替换，journal 损坏，以及 10 个持久边界注入故障后重开。Windows CI 还运行目标占用后释放重试与实际 junction 拒绝测试；平台执行结果以 Issue #24 exact-head 证据为准。

两项旧 T006 测试按本任务明确升级的 GUI 重名策略扩展：同内容已有目标现在必须真正备份并发布新 inode；“发布失败不能 Complete”改用文件/目录类型冲突，保留全部失败/旧内容/手动继续断言。没有删除失败测试或把旧内容相同作为完成证明。

本次按用户 Actions 成本规则将两个工作流改为 pull_request + workflow_dispatch；最终候选 PR 运行一套完整三平台 GPUI + windows-all，开发 commit 不自动产生 push 重复作业。原测试命令与平台门禁保留。真机、双 NAT、原生 UI 和最终发布验收仍属于后续任务，不能从此测试推断。

文件系统必须支持同卷 hard link 与原子 no-replace 备份。FAT 或接收子目录跨挂载点等不支持场景明确失败并保留恢复数据，不能以普通覆盖 rename 回退。
